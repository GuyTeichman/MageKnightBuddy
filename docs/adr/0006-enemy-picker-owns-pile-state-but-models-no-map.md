# The Enemy Picker owns pile state but models no map

The Enemy Picker (issue #178, see `../context-enemy-picker.md`) replaces the physical face-down token piles outright: the cardboard stays in the box, and the app is the source of both the randomness and the record of what is left in each **Token Pile**. That makes it authoritative in a way no other screen in this app is — a bug here doesn't produce a wrong number on a results page, it produces an illegal game.

Being authoritative over the piles tempts you into being authoritative over the board too, because three ordinary situations leave a token *out of the pile but not discarded*: a face-down garrison sitting on a revealed keep or mage tower for several Rounds, a rampaging orc or draconum standing on a space from tile reveal until someone kills it, and monsters at a monster den / spawning grounds / ruins that survive a failed fight and stay face up on the space (rulebook p.11, 3c). Handling those faithfully means knowing which token is on which space — the full board state that `docs/design/architecture.md` already rules out of scope and that [ADR-0004](0004-volkare-narrates-cards-not-simulates-board.md) declined to build for Volkare.

We chose to keep the pile authority and drop the board entirely:

- **Draw lazily.** A face-down token's identity is undetermined until it is flipped, so nothing is drawn when one is *placed*. The draw happens at the moment of the reveal, which is statistically identical and removes the need to track placements at all.
- **Discard immediately.** A drawn token goes straight to its pile's discard, exactly as the issue describes. There is no in-play state *in the pile* — nothing is held out of it — so there is nothing pile-side to forget to clear.
- **The Draw Log carries the memory.** Because the app forgets a token the instant it is drawn (pile-side), the log is the only record of which enemy is still standing where. It is correspondingly load-bearing rather than decorative: entries re-open the token, and each carries a **defeated** flag — a freshly drawn enemy is on the board (it was just revealed) and is marked defeated once beaten, the common reveal→defeat flow. That flag is *purely* a memory aid — it does not touch any pile (a defeated enemy was already discarded when it was drawn), so draw odds are identical however it is set.

## Consequences

- The player, not the app, remembers which enemy is on which space. A reader expecting the picker to track undefeated enemies — the obvious next feature — will be surprised, and that is deliberate: it is the same line [ADR-0004](0004-volkare-narrates-cards-not-simulates-board.md) drew for Volkare, applied to cardboard instead of cards.
- The Draw Log's on-the-board / defeated flag is the pressure valve for this. If it proves insufficient in real play, the fix is a better log, not a board model.
- Keeping the flag out of pile state is load-bearing for correctness: the moment it could hold a token back from the discard, the UI would silently change the probability distribution of every later draw.
- The pile state must survive app restarts for the length of a whole game (hours, across sessions), so it is persisted in Room rather than held in a `ViewModel` — the one place this feature is *less* casual than the issue's "reset button" framing suggests.
- **Draw with Replacement** (the issue's off-by-default toggle) is the deliberate escape hatch from all of the above: with it on, no pile state accumulates at all, which is what you want for pulling a one-off random enemy without perturbing a real game.
- **Faction tokens are the one documented exception** and the boundary is worth stating precisely, because "no in-play state" is otherwise easy to over-apply. The Apocalypse Dragon rulebook (p.6) has a drawn faction token *held* in the player's play area until spent, with unused ones worth 1 Fame at game end — so the picker keeps a held-inventory list for those, with a Spend action. What makes it consistent rather than a contradiction: this is flat inventory with no map involved, and unlike a flag on an enemy it must affect pile state, since a held token genuinely is neither in the pile nor in the discard. See `../context-enemy-picker.md`'s **Faction Token** entry.
